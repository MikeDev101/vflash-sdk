# Supplied firmware: identity and loader evidence

Local input: `A29L160ATV@TSOP48.BIN`, 2,097,152 bytes.
SHA-256: `467744d11dcf011762f41db4be60efbbd63cd2420003a1de41c421b4c88533ba`.
The user reported finding it on Internet Archive. No archive URL or vendor
authenticity was verified here. Analysis uses the existing local file, which is
Git-ignored and is never embedded in the SDK or generated homebrew disc.

## Address mapping

The reset code's data-copy table maps ROM offset `0x12000`, length `0x8DAD4`,
to SDRAM `0x1000FFF0`. The relevant routine can therefore be disassembled with
`runtime_address = ROM_offset + 0x0FFFDFF0`. Comparison against an emulator RAM
dump confirmed that mapping for the loader code.

To inspect the original file without extracting or modifying it:

```sh
arm-none-eabi-objdump -D -b binary -m arm -EL \
  --adjust-vma=0x0fffdff0 \
  --start-address=0x10012090 --stop-address=0x100126a8 \
  '/path/to/A29L160ATV@TSOP48.BIN'
```

Keep full disassembly and RAM captures in ignored build/research directories.
This document records findings rather than distributing firmware code.

## Loader findings

| Runtime address | Observed behavior |
| --- | --- |
| `0x100121B8..0x100121C0` | Requests an initial 512-byte read into a local buffer |
| `0x10012314..0x1001232C` | Extracts header `+8` into the destination variable |
| `0x10012338..0x10012350` | Extracts header `+4` into the full-read length |
| `0x1001235C..0x10012390` | Adds header `+8` and header `+12` to form the entry address |
| `0x1001239C..0x100123A0` | Calls a seek wrapper with `-512` to rewind the initial read |
| `0x10012494..0x100124A4` | Requests the full length into the header-specified destination |
| `0x10012668..0x10012670` | Reads CP15 control, then writes zero to it |
| `0x10012674..0x10012678` | Sets CPSR to `0xD3`: ARM SVC, IRQ/FIQ masked |
| `0x1001267C..0x1001268C` | Loads the calculated entry, places it in R0, and branches to it |

No BOOT magic comparison, REL/DBG parser, decompressor or whole-file checksum
was found in this inspected routine. That observation is scoped to this path.
Filesystem/CD reads have their own checks, including raw-sector integrity.
The generated minimal disc's successful launch proves REL/DBG metadata is not
required for this self-contained payload on this ROM/emulator combination.

The old upstream working note cites `0x100126B8` as a jump site. In this dump,
that address is a literal-pool word; the actual final branch is `0x1001268C`.
Consequently neither filename similarity nor upstream addresses should be used
as a substitute for hashing and examining the supplied firmware.

## Dynamic confirmation

With FlashEm commit `fb109dd01a49239c5884fcec60b9dc451fb651f8`, the local
commercial disc provided a baseline that reached its own BOOT stub and entry.
It was not modified or used as a template. The generated 176-sector homebrew
track subsequently booted through the same original firmware path, with no
`--load` or `--entry` override.

The following addresses and sector count are from the initial minimal probe,
not the current graphics/panic build. Resolve current application symbols from
its ELF. The custom-disc trace recorded the final firmware branch with R0 `0x10C00010`
and CPSR `0x000000D3`, then the stub at `0x10C00010`, startup at `0x10C00018`,
and C entry at `0x10C00048`. Startup set SP to `0x11000000`. At frame 1199,
physical SDRAM contained the expected data/status/marker and PC was in our
deliberate loop. The loader handoff occurred at approximately 6.705 seconds
of emulated time in the traced research run; wall time is host dependent.

## Raw-sector integrity validation

`tools/raw_cd.py` implements the CD-ROM reflected EDC polynomial `0xD8018001`,
GF(256) polynomial `0x11D`, and P/Q interleaving parameters. The sector layout
and parameters were checked against Neill Corlett's
[ECM implementation](https://github.com/qeedquan/ecm/blob/a8ec4e6dbdec53c24467f1eaef204c801c3cfb83/unecm.c).
ECM was compiled only as an external validation reference, not vendored or
linked into SDK tools.

An independently generated ECM sector with payload `bytes(range(256)) * 8`
at LBA 1234 has SHA-256
`91505d232ba2afe6cd1658227e9730c344d0a1be24b9def31babf88faedf8c12`;
the Python encoder matches it exactly. Five sectors at LBAs 0, 16, 100, 500,
and 27000 in the local Mode 1 disc also regenerated byte-for-byte from their
payload and LBA. Only the synthetic vector hash is included in automated tests.
